Approach 1
Zero-shot
Nothing to grade against — the optimizer rewrites your prompt from a one-line brief.
You provide: your prompt + a one-line description of the task.
Model receives: a rewritten, leaner instruction + the input. No examples.
Trade-off: fastest & cheapest to set up; weakest steering of the model.
Non-technical users
✓
Approach 2
Few-shot & rules
Can’t label a dataset, but you can show a few good answers and/or write the rules.
You provide: rules for a good answer, and/or a few example answers.
Model receives: the instruction + your examples as demonstrations + the input.
Trade-off: great for locking in style; example tokens are paid on every call.
Semi-technical users
✓
Approach 3
Training data
Strongest signal. GEPA grades candidate prompts against your known-correct answers.
You provide: rows of input → correct answer (e.g. from analytics/CRM).
Model receives: one dense, learned instruction + the input. No per-call examples.
Trade-off: best quality & generalization; costs an upfront optimization run.
Technical / power users

Model Standings

    
Measured latency per model, per role — so you choose models on evidence, not a hunch. Reflection is the role slow reasoning models punish hardest (it writes a full prompt rewrite each call), so it's the primary sort. Measurements are shared and refreshed each time diagnostics run.

    

      
Scope & how errors are reported

      Diagnostics probe text (chat-capable) models only — embedding, image, audio, rerank and moderation models can't answer a chat call, so they're skipped (and the run reports how many). For the models that are probed: an errored measurement is never shown — a role that failed reads as “—”, and a model whose every role failed is dropped from the table, counted only as “N hidden (errored)” in the header. So the table always reflects real, successful measurements; a green cell means that model genuinely responded at that latency.
